## 3. CRUD операции

| Операция | Реализация | Контрол |
|---|---|---|
| Create | Регистрирани потребители създават резервация | `reserve_book`, транзакция и заключване |
| Read | Четене на каталог, физически екземпляри и лични резервации | SELECT + RLS |
| Update | Отказ на резервация, промяна на статуса на екземпляра | `cancel_my_reservation` |
| Delete | Изтриване на вече отказана собствена резервация | DELETE с RLS, само при статус `cancelled` |

Отказът запазва историята чрез статус `cancelled`, а отделното действие „Изтрий от историята“ позволява ученикът да премахне само своя вече отказан запис.

## 4. Собствен алгоритъм: безопасно резервиране на екземпляр

**Вход:** ID на избраната книга и активен Supabase потребител.  
**Изход:** ID на резервация или ясно съобщение, че няма свободен екземпляр.

1. Проверява се дали потребителят е влязъл и дали книгата съществува.
2. Заявките за една и съща книга се подреждат с `pg_advisory_xact_lock`.
3. Проверява се дали потребителят няма вече активна резервация за книгата.
4. От свободните физически екземпляри се избира този с **най-малко ID**.
5. Избраният екземпляр се заключва с `FOR UPDATE` за текущата транзакция.
6. Статусът на екземпляра става `reserved`, след което се добавя запис в `reservations`.
7. Двете промени се изпълняват атомарно — при грешка не се запазва половин резервация.

При отказ се проверява собствеността на резервацията, статусът ѝ се променя на `cancelled`, а екземплярът се връща в статус `available`.

**Защо този алгоритъм:** при едновременни заявки два ученика не могат да получат един и същи екземпляр. Изборът на най-ниското ID осигурява повторяем и лесно обясним резултат.

**Код:** `docs/STAGE_3_MIGRATION.sql`; JavaScript: `script.js`.

## 5. Supabase

При проверка на 23.11.2026: 4 жанра, 6 книги, 11 екземпляра и нова таблица `reservations` (0 записа преди първата тестова резервация). RLS е включен; потребителите могат да виждат само собствените си резервации. Анонимната роля няма право да извиква `reserve_book` и `cancel_my_reservation`.

Двата RPC метода използват `SECURITY DEFINER`, защото трябва в една транзакция да променят `copies` и `reservations`. Това е умишлен привилегирован интерфейс: проверява `auth.uid()`, отхвърля anonymous claims, ограничава изпълнението до `authenticated`, при отказ проверява `user_id`, а функциите са с празен `search_path`. Security Advisor отбелязва тези два привилегировани метода с предупреждения, които трябва да бъдат прегледани при Етап 4.
